Inside a tool-call loop

Gemma 4 31B, run with thinking switched off, often re-sends a search that just failed, dozens of times in a row. Two real tasks show how such a loop starts and locks in, why a forced thought breaks it when four empty tokens mostly don't, and what changes when a fix runs over whole tasks.

In brief

  • A loop starts with a search that finds nothing, goes back to it, and locks in. After three identical calls, another copy follows 96% of the time.
  • Left to choose, the model stops thinking inside loops. Where it skipped the thought, forcing one makes 58% of calls escape, against 11%.
  • Adding an empty thought before every call shortens runs of copies but leaves the agent stuck just as often. It solves no more tasks.
  • Each stage has a known cause. Copies reinforce themselves, low-temperature sampling hardens the preference, and the model thinks when unsure, which it rarely is inside a loop.

The agent in these examples is Gemma 4 31B (int4, quantization-aware trained) working on real issues from four Python repositories: fastapi, requests, httpx and rich. It runs inside the coding-agent harness of the Gemma 4 agent competition on Kaggle, with thinking switched off, sampling at temperature 0.2. When it fails a task, the trace often ends the same way: one tool call, sent again and again, getting the same answer each time.

A useful picture is someone hunting for their keys who keeps opening the same drawer. For a person, remembering “I already looked there” ends the search. For the model it works the other way round. Its record of having opened the drawer is a pattern to copy, and every copy makes the next one more likely.

How the agent works

The agent is a loop between the model and a harness. At each step the model reads the whole history (the task, every earlier tool call, and what each call returned) and writes one new call. The harness runs it and appends the result.

Gemma 4 can also write a private thought before a call, between <|channel>thought and <channel|>. With thinking switched off, the chat template inserts an empty thought, four tokens long, and only before the first call. Later calls follow the last tool result directly, and the model decides for itself whether to write the empty thought first.

A loop, call by call

Task fastapi_14246 asks for a fix to how FastAPI separates input and output schemas for nested models. In the run below the agent failed, and almost all of its call budget went into one loop.

The run shows the four stages of a loop in order.

  1. Onset. A search for something that isn’t there finds nothing (call 8), and the model tries a variant (call 9).
  2. Return. It goes back to the search that already failed (call 10). Most loops start this way.
  3. Lock-in. Each copy makes the next one likelier. Across 109 tasks, once the agent has sent the same call twice in a row, a third copy follows 77–78% of the time; after three or more, another copy follows 96% of the time.
  4. Exit. Nothing inside the loop ends it. The budget warning arrives, and the agent submits an empty patch.

What would the model do next?

A replay test (we call it Gate 1) takes a recorded state, meaning the history just before one call, changes the context in one way, and asks the same weights what they would do next. It reports two things. The first is p(copy), the probability the model gives to sending the copy again at the run’s sampling settings. The second is one sampled call, labelled as a copy or a new call. Table 1 shows four states from this loop.

Okay, I’m looking for where separate_input_output_schemas is used to handle nested models. […] Let’s find where get_schema_from_model_field is defined. It’s imported from fastapi._compat.

Next call: grep -r "def get_schema_from_model_field" fastapi/_compat/

T-open’s thought at call 35 (excerpt)

Okay, I’ve spent some time trying to find get_openapi_route in fastapi/openapi/utils.py but it seems I was mistaken about the function name or it’s not there.

Next call: grep -n "separate_input_output_schemas" fastapi/openapi/utils.py

The first thought never mentions the loop. It re-plans from the task and picks a different next step. The second names the dead end outright.

Why each context works or fails

  • The note says exactly the right thing and changes nothing. Instructions don’t reach a model that has locked in.
  • The hindsight hint helps more as the loop goes on, but the copy stays the likeliest call.
  • The empty thought halves p(copy) on average, but not in this task: at the 7th and 15th copies it changes nothing.
  • Own choice fails because the model never thinks. Free to write a thought, it went straight to the call at every one of these states.
  • Deleting the copies and forcing a thought both work. One removes the pattern the model is copying. The other makes it stop and re-plan.

What the averages say

The loop above is an extreme case, but the same picture holds over all 581 replay states in 70 tasks. Left to choose, the model writes a real thought at 72% of second copies, at only 23% of third-or-later copies, and at 6% of malformed calls. Its own thinking switches off inside loops. That alone doesn’t show a thought would have helped there, so T-open forces one at every state.

Where the model chose to think, forcing a thought changes nothing (62% against 63%). Where it chose not to, a forced thought escapes 58% of the time against 11%. The states the model skips are just as fixable as the ones it picks. Its decision not to think follows its confidence, and that confidence says nothing about whether a thought would help.

Switching thinking on does nothing by itself (p(copy) 0.97). Four empty tokens halve p(copy) but still leave most samples stuck. Only a real thought breaks the lock: p(copy) falls to 0.11 and 69% of samples escape.

Two checks on the forced thoughts. None of the 581 fell into a token loop: in none is more than half of the text repeated (measured on 8-token sequences), the same as for thoughts the model writes on its own. The cost on calls that were fine is small. After an empty search, escape goes from 92% to 85%; on routine calls, from 98% to 96%.

The same idea over whole tasks

The replay looks one call ahead. A closed-loop test lets the agent run whole tasks with a change in place, each step feeding the next. We ran one. The always-block template adds the empty thought before every call. It is the edit proposed in Hugging Face PR #147 for the Gemma 4 templates, and Google’s prompt-formatting guide also suggests adding an empty thinking token. The control arm ran the same agent with the model’s own template, on the same 109 tasks and the same hardware.

Counted as runs of identical calls, the always-block run holds seven runs of three or more, and seven copy starts. Six of those runs end without a budget warning, compaction or task end. Yet the agent never leaves the dead end: it is one stuck stretch of 52 calls. The control run holds one run and one copy start. Table 2 shows the same pattern over all tasks.

The number of stuck stretches barely moves, and they occur in about the same tasks. Inside them, the agent hops between stale calls more often, so runs of identical calls get shorter and more numerous, and copy starts nearly double. Resolved tasks don’t change. Of the 53 runs that ended without a warning, compaction or task end, 29 went straight into another stale call, and only 5 were in tasks that ended resolved.

The replay had already hinted at this. One step ahead, the empty thought halved p(copy) at third-or-later copies (0.95 to 0.50), yet 80% of its sampled calls stayed stale. Over whole tasks, another copy follows three or more 84–92% of the time. The sampled call was the better guide.

Why the model stops writing the empty thought

In the control arm the model writes the empty thought itself before most early calls, then less and less (Figure 7). The template strips past empty thoughts from the history, so as a task goes on, the model sees a longer and longer record of calls with no thought in front of them. Agents tend to imitate their own earlier turns, and more so as the context grows; Wan et al. call this conversational inertia. That would produce this drift. It is a hypothesis we haven’t tested yet, and the second open question below describes the test.

How this connects to prior work

Loops in agents are well documented. These examples add a measurement at the level of single decisions, interventions compared at the same states, and a whole-task test of one fix. Table 3 maps each part of the picture to the closest prior work.

Why loops happen

No single theory explains agent loops, but each stage of the loops above matches a known principle, and the principles fit together. Each part below says how firm it is: established in prior work, measured in our data, or a hypothesis that fits the data but hasn’t been tested.

Established; measured here

Lock-in is a self-reinforcing process

Each copy multiplies the odds of the next one (Figure 8). Repetition in text follows the same law: a repeated phrase becomes more likely with each repetition (Holtzman et al.), and the effect then saturates (Xu et al.). A Pólya urn behaves this way: every ball drawn adds another ball of its colour.

This also explains how long loops last. If each call continues the loop with probability q, the rest of the run is geometric, with a mean of 1/(1 − q) further copies.

  • Control, q = 0.957: about 23 more calls, more than most loops have left before the budget warning. So 48 of the 55 runs of three or more end at an outside event (the budget warning, a compaction or the end of the task), and only 7 end on their own.
  • Always-block, q = 0.89: about 9 more calls, and 6 on dev tasks, where q is 0.84.
  • Near q = 1 the mean is very sensitive to q. A modest drop cuts runs sharply. That is the fragmentation in Table 2: shorter runs, but about as many stuck stretches.

Hypothesis

The repeated result cues the copy

Induction heads (Olsson et al.) find where the current context appeared before and copy what followed: A B … A → B. In our loops, 91% of stale repeats got exactly the result their earlier copy got. So the context ends with a result that appeared before, and last time that result was followed by the same call. The repeated result doesn’t tell the model to stop. It tells the copying circuit what to send.

Four observations fit this, though none proves it:

  • The jump at the third copy. At the first repeat, the result has never been followed by the call, so the cue doesn’t exist yet; from the third call on, it does. At Google’s recommended sampling (temperature 1), the model’s own p(copy) is 0.26 at second copies and 0.73 at third-or-later ones.
  • Changing the last result weakens the copy. The note and the hindsight hint both add text to it, and both halve p(copy).
  • So does the empty thought. It puts four tokens between the result and the call, tokens that never appear in the history because past ones are stripped.
  • The hopping in Figure 5 is a copied pattern. After grep B’s empty result, the history already holds “B’s result, then A” (calls 7 and 8).

The statistical version of the same idea: in-context learning behaves like Bayesian inference over a hidden concept (Xie et al.). The agent’s own past calls count as examples of what it does here, so each copy is more evidence for sending the same call again. Sinha et al.’s self-conditioning and Wan et al.’s conversational inertia are this effect seen in agents. A clean test, for later: make each repeated result differ in a way that means nothing, such as a request id, and see whether lock-in collapses.

Established; measured here

Low temperature turns a preference into a certainty

At temperature T, the sampler draws from p(x)1/T, renormalised. At T = 0.2 the odds between two calls are raised to the fifth power, so 2 : 1 becomes 32 : 1. The replay separates this from the model’s own preference at the same states (Table 4).

So lock-in has two parts. In-context reinforcement raises the model’s own preference for the copy, from 0.26 at the second copy to 0.73 at the third and later. Low temperature then makes the most likely call nearly certain; at the second copy, most of the 78% lock-in comes from the sampler. Near-greedy decoding of a self-reinforcing process settles into a cycle, which is the classic degeneration result (Holtzman et al.). Pipis et al. call temperature “a stopgap”, and in these terms it removes the second part and leaves the first. Sampling at temperature 1 would weaken lock-in, not end it: the only whole-task run at temperature 1, with a different agent prompt, still locked in 73% of the time.

Established principle; seen in our traces

Loops start with a call that can’t teach anything

In a deterministic environment, an identical read-only call returns what it returned before, so it carries no new information. A rational searcher never makes one, and a stale repeat is exactly such a call. Next-token training has no term for new information: the model picks what is likely given the context. In our traces the onset runs like this:

  1. The model searches for something it strongly believes exists, such as a plausible function name that isn’t in the file.
  2. The empty result contradicts that belief but gives almost no text to condition on.
  3. It tries variants: after an empty search, the next call is a variant 78% of the time. When the variants also fail, it returns to its first and most likely query. 114 of 131 loops start by re-sending a call from two or more calls back.

Liu et al. show the disconnect directly: shuffling an agent’s past actions changes its score by only 2.55 points, so it isn’t tracking which call produced which result.

Learning theory explains why this shows up once the agent is off track. A policy trained to imitate experts errs at some rate ε per step, and each error takes it somewhere the experts never went, with nothing to imitate. Over a horizon of H steps its errors grow like εH2 rather than εH (Ross, Gordon & Bagnell). A made-up function name is such a place, and copying its own recent behaviour is the fallback there. Pipis et al. report the same in reasoning models: when progress is hard to learn, an easy repeating action keeps its probability, and students distilled from a teacher loop more than the teacher does (30% against 4%).

Measured here

The model thinks when unsure, and a loop is where it is most sure

Metareasoning (Russell & Wefald) says to deliberate when the expected gain from thinking exceeds its cost, which they call the value of computation. Our model instead thinks when it is uncertain. Free to choose, it writes a thought at 72% of second copies and 23% of third-or-later copies, while p(copy) rises from 0.77 to 0.94. At a loop state the current action is worth nothing, and a thought improves it most of the time, so thinking is worth most exactly where the model is most certain. Figure 3 measures this: a forced thought helps as much where the model skipped thinking (58%) as where it chose to think (63%).

Any trigger built on confidence or entropy has this blind spot; HRBench calls the failures “confident wrong answers”. A useful trigger reads a signal tied to the benefit, such as “my last call returned the same result as before”. A harness sees that easily, so a controller outside the model can decide when to think.

What is specific to tool calls and code

  • The environment echoes. Each cycle adds two identical pieces to the context, the call and its identical result, and nothing outside disturbs them. In free text only the model’s own words repeat.
  • Calls are short, rigid strings. Copying a whole call is cheap and always gives valid syntax.
  • The worst results are the emptiest. A grep that finds nothing returns the same featureless answer every time: a clean cue for copying, and almost nothing to reason from. In one recorded run, 270 of 580 repeated shell commands got nothing back. Sethi et al. found that an ok status with an empty payload led to 45% fabricated answers, against 0% for an explicit error.
  • Contexts grow. The repeated block grows while the task statement recedes. Compaction cuts both ways: it deletes the copies, and with them the evidence of failure; 44% of loops re-send a call that compaction had hidden.

One model for all of it

A stylised model, not a fitted one, puts the pieces together. The probability of each candidate call c is

P(next call = c) ∝ exp( [ s(c) + λ·n(c) + μ·m(c) ] / T )
s(c)
the model’s prior for call c, given the task
n(c)
copies of c already in the context
m(c)
1 when the last result matches what came before c the previous time, otherwise 0
λ, μ
how strongly the copies and the cue pull
T
the sampling temperature

Each lever we tested changes one part of it (Table 5). What the model has no term for is new information, or which call produced which result. That gap is where the most promising fixes would act.

How firm each piece is:

Established elsewhere
Self-reinforcement and its saturation; degeneration at low temperature; compounding errors in imitation; confidence-based triggers failing on confident mistakes.
Measured in our data
The lock-in curve; the split between reinforcement and temperature; the thinking trigger’s failure; the onset at calls that can’t teach anything.
Fits, untested
The repeated result as the copy cue; the A/B cycle as a copied pattern; conversational inertia behind the drift.

Open questions

1. Why does the always-block template double copy starts?

Where it came from
Table 2. Copy starts went from 36 to 64 on dev tasks and from 35 to 56 on rich ones. That contradicts a prediction of fewer, drawn from Gumaan and Liu et al., and the replay, where the empty thought halved p(copy).
A first look
It is mostly fragmentation. Counting stuck stretches instead of runs, the number barely changes (36 to 41, and 36 to 29), in about the same tasks. 52 of the 64 dev copy starts fall inside a stretch, against 28 of 36 in the control arm. Figure 5 shows the mechanism: inside one stretch, each hop back to grep A starts a new run.
What’s left
Copy starts outside stuck stretches rose from 8 to 12 on dev tasks and from 8 to 11 on rich ones. Those counts are small.

2. Does the drift reset after a compaction?

Where it came from
The drift in Figure 7, the template’s rule of stripping past empty thoughts, and Wan et al.’s conversational inertia.
How to answer it
A compaction replaces much of the history with a summary. If the model imitates its visible history, it should start writing the empty thought again right after a compaction. If it doesn’t, the drift depends on how deep the agent is in the task. The control arm’s call records already hold both pieces.
Why it matters
It would explain the drift. The same inertia would also explain another pattern in these runs: once the harness quietly accepts a call written in a slightly wrong format, later calls copy that format.

3. Would a forced thought at stuck states turn escapes into resolved tasks?

Where it came from
T-open is the strongest lever, but it was measured one step ahead. The one lever we ran over whole tasks lost most of its one-step effect, and its escapes rarely led anywhere.
What prior work says
Escapes that bring nothing new don’t help (SWE-smith, Liu et al., Gumaan, Second Thought). Escapes that bring information help a little: a restart that keeps the earlier diff gave Gemma 4 31B 3.0 more points (Fail-Fast), and showing the remaining budget added 18.6 (BATS).
Why it is still open
A real thought may be the kind that brings information. The thought at call 35 noticed the dead end, which an empty thought cannot do. The ceiling is low, though: removing every loop would gain about 2 of 70 dev tasks.
What it needs
A controller that forces a thought when it sees a copy, run over whole tasks.

Terms used on this page

Behaviour

Stale repeat
A call identical to an earlier one (same tool and arguments) with no successful edit in between, so it must return the same result.
Copy, run, copy start
A copy repeats the call just before. A run is a stretch of identical calls; a copy start is the second identical call in a row.
Return
A stale repeat of an earlier call that wasn’t the one just before. Most loops start this way.
Lock-in
The chance that the next call is one more copy, given that the last few calls were identical.
Stuck stretch
Three or more bad calls in a row, identical or not. A bad call is a stale repeat or a malformed call.
Malformed call
A call with unknown or missing argument names.
Escape
The sampled call is a valid call that is neither a stale repeat nor malformed.

Experiments

State
One decision point: the history just before a call, plus the call the model made there. Each state has a class, such as second copy, third-or-later copy, return, after an empty search, or routine.
Replay (Gate 1)
Take a recorded state, change the context in one way, and ask the same weights what they would do next. It looks one call ahead.
p(copy)
The probability the model gives the copy at the run’s sampling settings (temperature 0.2, top-p 0.95, top-k 64). 0.00 means the copy can no longer be sampled.
Closed loop
Whole tasks run with a change in place, each step feeding the next.
Student
The model as it ran, with thinking off.
T-think
Thinking on; the model decides whether to write a thought.
T-open
Thinking on, with the thought already opened. It can’t close before 32 tokens and runs to at most 512.
block, C-none
The empty thought forced before the call, with thinking off (block) or on (C-none).
Note, T-hint
Text added to the last tool result: a factual note, or a hint that names the exact call and what it returned.
Dedup
The history with the earlier copies of the last call deleted.
Control, always-block
The closed-loop pair: the model’s own template, or one that adds the empty thought before every call.

Harness and analysis

Budget warning
The harness’s notice that the call budget is running out. In these runs it appears from call 49.
Compaction
The harness summarises old history when the context gets long.
Session limit
A 4-minute wall-clock limit per task.
Self-selection
The model choosing where to think. It mixes two questions: does a thought help, and where does the model choose to think?
Drift
The model writing the empty thought itself less and less as a task goes on.
Ceiling
The most a perfect loop fix could gain: tasks that loop and fail here but that another run solved. About 2 of 70 dev tasks.

Theory

Induction head
An attention pattern that finds where the current context appeared before and copies what followed it.
Temperature
Sampling from p(x)1/T, renormalised. Below 1 it sharpens the distribution; at 0.2, the odds between two options are raised to the fifth power.
Value of computation
The expected gain from thinking before acting, minus the cost of thinking.

About the data

  • Model: Gemma 4 31B, int4 quantization-aware trained, served with vLLM; thinking off; temperature 0.2, top-p 0.95, top-k 64.
  • Replay: 581 states in 70 tasks from one recorded run of the agent with thinking off (the source of Figures 2–4 and Table 1).
  • Closed loop: one run per arm, 109 tasks (70 dev, 39 rich), four tasks at a time on one A100 (Figures 5–7 and Table 2).
  • Limits: one run per arm, one model and one temperature. T-open was measured one step ahead only. The malformed-call results rest on 4 tasks. The 4-minute session limit ended 5–15% of tasks per arm and task group.
